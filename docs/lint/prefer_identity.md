# `prefer_identity`

A `serial`, `bigserial` or `smallserial` column instead of an identity
column.

| Level | Applies to | Fix |
|---|---|---|
| off | the final schema | — |

## Example

```sql
-- migrations/001_init.sql
CREATE TABLE events (
    id bigserial PRIMARY KEY,
    position serial NOT NULL
);
```

```
info[prefer_identity]: public.events.id is a serial column
   ╭─[migrations/001_init.sql:1:1]
 1 │ CREATE TABLE events (
   · ─────────────────────
 2 │     id bigserial PRIMARY KEY,
   · ─────────────────────────────
 3 │     position serial NOT NULL
   · ────────────────────────────
 4 │ );
   · ─
   ╰────
  help: use GENERATED BY DEFAULT AS IDENTITY: the sequence then belongs to the column (permissions, dumps, ALTER TYPE follow it)
```

`position` gets the same finding. When the migration is unchanged from
`--previous-deployment`, the help reads
`use GENERATED BY DEFAULT AS IDENTITY in a new migration`.

## Why

`serial` is an `integer` column plus a separate sequence and a
`DEFAULT nextval(…)`. The sequence needs its own grants, the default can be
dropped or changed on its own, and a hand-inserted id doesn't advance it,
so a later insert collides. An identity column (`GENERATED BY DEFAULT AS
IDENTITY`, or `ALWAYS`) owns its sequence and is what PostgreSQL recommends.

Off by default: `serial` works, and converting existing columns is churn.

## Reported when

A table column's default is `nextval()` of a sequence owned by that column,
and the column is not an identity column. The finding is placed on the last
statement that gave the column its type (`CREATE TABLE`, `ADD COLUMN`,
`ALTER COLUMN … TYPE`).

## Not reported

- Identity columns: `id bigint GENERATED BY DEFAULT AS IDENTITY`.
- A default on a sequence the column doesn't own:
  `position integer NOT NULL DEFAULT nextval('shared_seq')`.
- Partitions and inheritance children (the parent is reported), tables in
  `pg_*` schemas or `information_schema`, columns from `extra_migrations`.

## Configuration

```toml
# Cargo.toml
[package.metadata.typedpg.lint]
prefer_identity = "info"   # error | warning | info | off
```
```json
// typedpg.config.json
{ "lint": { "preferIdentity": "info" } }
```

Allow one statement by putting `-- typedpg-lint: allow(prefer_identity)`
before it in the migration file; it covers every column of that statement.
See [Configuring rules](README.md#configuring-rules).
