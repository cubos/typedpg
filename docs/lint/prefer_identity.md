# `prefer_identity`

A `serial` / `bigserial` / `smallserial` column, where a SQL-standard identity column (`GENERATED … AS IDENTITY`) does the same job without a loose sequence.

| | |
|---|---|
| Default level | off (reports at info when enabled with a level) |
| Applies to | the final schema |
| Fix | no |

## Why

`serial` is not a type. It is shorthand for an `integer` column with `DEFAULT nextval('t_id_seq')` and a separately created sequence marked as owned by the column. The pieces stay separate objects: privileges on the sequence must be granted on their own (an `INSERT` grant on the table is not enough), the default can be dropped or changed independently, and an explicit value inserted by hand doesn't advance the sequence, so a later insert collides with it.

An identity column (`GENERATED BY DEFAULT AS IDENTITY`, or `ALWAYS` to reject explicit values without `OVERRIDING SYSTEM VALUE`) makes the sequence part of the column: it follows the column through permissions, dumps and `ALTER COLUMN … TYPE`, and the SQL standard defines it. PostgreSQL's documentation recommends identity columns for new applications.

Off by default: `serial` works, and changing existing columns is churn.

## What it reports

Every column of an ordinary or partitioned table in a user schema of the final schema whose default is `nextval()` of a sequence owned by that same column — what the `serial` shorthands create — and that is not an identity column. A `DEFAULT nextval('shared_seq')` on a sequence the column doesn't own is not reported. Partitions and inheritance children are skipped.

### Placement and `--previous-deployment`

A schema rule: it reads the columns after the last migration and reports on the last statement that gave the column its type (`CREATE TABLE`, `ADD COLUMN`, `ALTER COLUMN … TYPE`). When that statement is in a migration file unchanged from `--previous-deployment <ref>` (or matching `lint.ignore`), the finding stays there with the help line `use GENERATED BY DEFAULT AS IDENTITY in a new migration`. Columns from `extra_migrations` are not reported.

## Examples

### Bad

With the rule enabled (`prefer_identity = "info"`):

```sql
-- migrations/0001_init.sql
CREATE TABLE events (
    id bigserial PRIMARY KEY,
    position serial NOT NULL
);
```

```text

   ╭─[migrations/0001_init.sql:1:1]

 4 │ );

  help: use GENERATED BY DEFAULT AS IDENTITY: the sequence then belongs to the column (permissions, dumps, ALTER TYPE follow it)

info[prefer_identity]: public.events."position" is a serial column

 3 │     position serial NOT NULL

 4 │ );
   · ─

  help: use GENERATED BY DEFAULT AS IDENTITY: the sequence then belongs to the column (permissions, dumps, ALTER TYPE follow it)
```

### Good

```sql
CREATE SEQUENCE shared_seq;
CREATE TABLE events (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    -- A sequence shared between tables is not a serial column.
    position integer NOT NULL DEFAULT nextval('shared_seq')
);
```

## When it stays silent

- The rule is off (the default).
- The column is an identity column, or its default uses a sequence it doesn't own.
- The column is in a partition, an inheritance child or a table of a `pg_*` schema or `information_schema`, or comes from `extra_migrations`.
- An allow comment on the statement that gave the column its type (it covers every column of that statement).

## Configuration

```toml
# Cargo.toml
[package.metadata.typedpg.lint]
prefer_identity = "info"   # "error", "warning", "info" or "off" (default)
```

```json
// typedpg.config.json
{ "lint": { "preferIdentity": "info" } }
```

For one statement:

```sql
-- typedpg-lint: allow(prefer_identity)
CREATE TABLE legacy_events (id serial PRIMARY KEY);
```

See [Configuring rules](README.md#configuring-rules) for `fail_on` / `failOn`, `ignore` and `--previous-deployment`.
