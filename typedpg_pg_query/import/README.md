# Importing PostgreSQL

`import/` rebuilds [`postgres/`](../postgres), the unmodified PostgreSQL
sources typedpg compiles. Nothing under `postgres/` is hand-edited: every
file there is copied from the release tarball or generated by this tooling,
so a re-import reproduces it byte for byte.

The crate's `build.rs` compiles `import/FILES`, `postgres/typedpg/*.c`,
`csrc/*.c`, `csrc/pg/*.c` and `csrc/plpgsql/*.c` for every target, plus the
`import/FILES.windows` sources on Windows. Nothing comes from libpg_query any
more, and the repository no longer carries it as a submodule.

## Prerequisites

- A C compiler, GNU make, perl, python3, curl, tar and sha256sum.
- **bison** and **flex** (PostgreSQL's `configure` and generated parsers need
  them), plus **bindgen** and **clang** (the Rust bindings of the node structs
  are generated with `bindgen`, which loads libclang). They are often not
  installed system-wide; with Nix, run everything through a shell that provides
  them:

  ```sh
  nix shell nixpkgs#bison nixpkgs#flex nixpkgs#rust-bindgen nixpkgs#clang \
    -c typedpg_pg_query/import/import.sh
  ```

- Network access to `https://ftp.postgresql.org/pub/source/` for the first run
  (the tarball is cached under `${TMPDIR:-/tmp}/typedpg-import-<version>` and
  reused afterwards).

## Running the import

```sh
typedpg_pg_query/import/import.sh
```

No arguments. The version comes from [`POSTGRES_VERSION`](../POSTGRES_VERSION)
and the expected tarball hash from [`POSTGRES_SHA256`](../POSTGRES_SHA256).

The script:

1. downloads `postgresql-<version>.tar.bz2` (if not cached) and verifies it
   against the pinned hash in `POSTGRES_SHA256`, failing on any mismatch;
2. extracts and configures the release (`--without-icu --without-readline
   --without-zlib --without-zstd --without-lz4 --without-openssl`);
3. generates PostgreSQL's derived headers, the function-manager table and
   the parsers with make, bison and flex (`gram.c`, `scan.c`, `kwlist_d.h`,
   `pl_gram.c`, `plerrcodes.h`, `fmgrtab.c`, ...);
4. deletes and recreates `postgres/` entirely, then copies every file in
   [`FILES`](FILES) and [`FILES.windows`](FILES.windows) at its PostgreSQL
   path, plus the private/generated headers next to those sources, the `.c`
   files they `#include`, `COPYRIGHT` and `VERSION`;
5. copies the include tree, appends the portable overrides to configure's
   `pg_config.h` and replaces `pg_config_os.h`
   ([`pg_config_overrides.h`](pg_config_overrides.h),
   [`pg_config_os.h`](pg_config_os.h); see [Platforms](#platforms)), then
   trims the tree to the headers actually used (`gcc -MM` over the sources,
   `csrc/pg/*.c`, `postgres/typedpg/*.c`, plus
   [`EXTRA_HEADERS`](EXTRA_HEADERS));
6. writes `postgres/typedpg/builtin_catalog.c` from the release's
   `postgres.bki` — the `pg_type`, `pg_namespace` and built-in `pg_collation`
   rows ([`gen_catalog.py`](gen_catalog.py));
7. writes `postgres/typedpg/stubs_functions.c` and `stubs_variables.c` for the
   symbols the compiled code references but the crate does not define
   ([`gen_stubs.sh`](gen_stubs.sh));
8. writes `postgres/typedpg/bindings.rs`, the bindgen bindings of the node
   structs, `List`/`ListCell`/`Bitmapset`, `NodeTag`, the enums the node fields
   use and the value nodes. Only those types are allowlisted; bindgen pulls in
   what they reference. The output uses `::core::ffi` types, `consts`-style
   enums, wrapped unsafe operations and no layout tests or doc comments, and its
   version banner is stripped so the file is reproducible. A second bindgen run
   appends PL/pgSQL's compiled-function structs (`plpgsql.h`'s `PLpgSQL_*`
   types, which `src/plpgsql/convert.rs` reads): it allowlists those and the
   few types their fields name beyond the node bindings, without recursion,
   and keeps the runtime-only ones opaque (`plpgsql.h` declares the executor's
   node structs, which the first run's node tag list would otherwise pull in
   by the hundred);
9. fails if any build-machine path (`/tmp/...`, `/home/...`, `/nix/store/...`)
   leaked into the tree.

Running it twice produces identical trees; this is safe to diff:

```sh
cp -a typedpg_pg_query/postgres /tmp/postgres-before
typedpg_pg_query/import/import.sh
diff -r /tmp/postgres-before typedpg_pg_query/postgres
```

## Link check

```sh
typedpg_pg_query/import/check.sh
```

Compiles every file in `FILES`, every `csrc/pg/*.c` and every
`postgres/typedpg/*.c` into one shared object with `-Wl,--no-undefined`
(libc and libm only). It checks the import machine's target (the same one
`build.rs` compiles natively); the other targets need their own C builds (the
release workflow does them). It exits non-zero if the stub generation misses a
symbol.

## Platforms

The release workflow builds `typedpg` on glibc and musl Linux (x86_64 and
aarch64), macOS (x86_64 and aarch64) and Windows x64/MSVC, all from the one
tree this directory produces. configure runs only once, on the import machine
(x86_64 Linux, glibc), so the platform-dependent answers are committed:

- [`pg_config_overrides.h`](pg_config_overrides.h) is appended to
  `postgres/include/pg_config.h`. It corrects the defines that describe the
  import machine's libc and compiler — strlcpy/strlcat, strchrnul, strerror_r,
  execinfo, the Unix-only headers, MSVC's missing compiler features and
  __int128, the x86-only cpuid/popcount code — with preprocessor conditions,
  each block commented with the reason. It mirrors what PostgreSQL's own
  `meson.build` checks would find on each target and what libpg_query's
  hand-maintained `pg_config.h` sets.
- [`pg_config_os.h`](pg_config_os.h) replaces configure's copy of
  `port/linux.h` with a dispatcher to `port/linux.h`, `port/darwin.h` or
  `port/win32.h`. On Windows it also undefines `PGDLLIMPORT`/`PGDLLEXPORT`:
  the sources go into a static library, not a DLL.
- [`EXTRA_HEADERS`](EXTRA_HEADERS) lists the headers the Linux `gcc -MM` trim
  cannot see but the other targets include: the other port files, the atomics
  backends for arm/ppc/MSVC, and PostgreSQL's stand-ins for the Windows system
  headers (`port/win32/`, `port/win32_msvc/`). `build.rs` puts the latter two
  on the include path for Windows, as PostgreSQL's meson build does.
- [`FILES.windows`](FILES.windows) lists the sources only Windows compiles:
  `open.c`, `win32error.c`, `win32ntdll.c`, `win32gettimeofday.c`,
  `win32pread.c` and `win32pwrite.c`. They are not part of the `gcc -MM` trim
  (they include Windows SDK headers). The symbols those sources reference, and
  the few Windows-only references in the imported code (`pg_signal_queue`,
  `pgwin32_dispatch_queued_signals`, `pgwin32_is_service`, `pg_usleep`,
  `pg_codepage_to_encoding`, `event_source`), are defined in
  [`csrc/pg/win32.c`](../csrc/pg/win32.c) and
  [`csrc/pg/vars.c`](../csrc/pg/vars.c); they are absent or unused on the other
  targets, and the generated stubs run on Linux and cannot see them.
- `build.rs` picks the compiler mode (gnu11 or MSVC's `/std:c11`), `WIN32`
  and the MSVC defines (`_CRT_SECURE_NO_DEPRECATE`, ...), and the system
  libraries: `advapi32` on Windows (the event log in `elog.c`), `libm` on
  Linux, and none on macOS (libSystem has both).

`src/port/strlcpy.c` is in `FILES`, as PostgreSQL builds it where the libc
lacks `strlcpy` (glibc before 2.38, Windows). Where the libc has it, `build.rs`
leaves the file out: compiling OpenBSD's definition there breaks when
`<string.h>` makes `strlcpy` a macro under `_FORTIFY_SOURCE` (macOS builds).
`build.rs` asks the target compiler whether `pg_config.h` says
`HAVE_DECL_STRLCPY` — the same test `port.h` uses — instead of guessing from
the target triple.

## What gets imported

- `postgres/VERSION`, `postgres/COPYRIGHT`.
- The 78 files listed in [`FILES`](FILES), whole and unmodified, at their
  PostgreSQL paths under `src/backend/`, `src/common/`, `src/port/` and
  `src/pl/plpgsql/src/`.
- The private and generated headers next to them (`gram.h`, `kwlist_d.h`,
  `pl_gram.h`, `plerrcodes.h`, `pl_*_kwlist_d.h`, the nodes
  `*.funcs.c` / `*.switch.c`, and the generated `fmgrtab.c` /
  `errcodes.h` / `fmgroids.h` family next to `src/backend/utils/`).
- `postgres/include/`: only the headers the compiled code uses, plus
  [`EXTRA_HEADERS`](EXTRA_HEADERS).
- `postgres/typedpg/`: `builtin_catalog.c` (`pg_type`, `pg_namespace` and
  the built-in collations), `stubs_functions.c`, `stubs_variables.c` and
  `bindings.rs` (all generated).

The hand-written code lives in [`csrc/`](../csrc). `csrc/catalog.c` and
`csrc/typedpg_catalog.h` bridge the caller's Rust `Catalog` into the syscache
and build the catalog rows as heap tuples; `csrc/pg/` holds the server
services the copied sources call (`vars.c` for globals, `server.c` for the
superuser ACL checks, the syscache callbacks and no-op locks, `syscache.c` for
the syscache itself, `type_cache.c` for `lookup_type_cache`, `parse_defaults.c`
for the parameter-default transformers the crate skips, and `shim.c` for the
C entry points); `csrc/plpgsql/` holds libpg_query's PL/pgSQL driver
(BSD-3-Clause, see the LICENSE there), adapted. `gen_stubs.sh`
compiles all of them too, so anything they define is subtracted from the stub
list; adding a file there needs no other change.

## Adding a file to FILES

1. Append its path relative to the PostgreSQL source root, e.g.
   `src/backend/utils/adt/date.c`.
2. Run `import.sh` again. The file and the headers it needs are picked up
   automatically; the stub lists shrink to what is still missing.
3. Run `check.sh`. If it reports undefined symbols, the source needs another
   file (or an override in `csrc/pg/`), not a stub.
4. Commit `FILES` and the regenerated `postgres/` together.

`gen_stubs.sh` subtracts the symbols the crate's Rust side defines
(`typedpg_remaining_stack`, src/stack.rs) from the stub list by hand.

Removing a line removes the file on the next import (the output tree is
recreated from scratch).

## Bumping the version

1. Set [`POSTGRES_VERSION`](../POSTGRES_VERSION) to the new release.
2. Download `https://ftp.postgresql.org/pub/source/v<version>/postgresql-<version>.tar.bz2`
   and put its sha256 in [`POSTGRES_SHA256`](../POSTGRES_SHA256) (the server's
   `.sha256` file has the same value; the import verifies against the pinned
   copy, not the network).
3. Run `import.sh` and `check.sh`.
4. Commit `POSTGRES_VERSION`, `POSTGRES_SHA256` and the regenerated
   `postgres/` tree.

If a new release moves or drops a file listed in `FILES`, the import fails
with the missing path; adjust the list and re-run.

## Notes

- `EXTRA_HEADERS` lists headers kept even when no compiled source includes
  them: the code generation reads the node and parser definitions, later
  phases need some of the others, and the other targets' port and atomics
  headers are only reachable from their own preprocessor paths (see
  [Platforms](#platforms)). Paths are relative to `postgres/include/`; `#`
  starts a comment, as in `FILES` and `FILES.windows`.
- `import.sh` also refuses to continue if a `FILES` or `FILES.windows` entry is
  missing from the release, or if bison, flex or another required tool is not
  on `PATH`.
- `postgres/include/pg_config_manual.h` keeps PostgreSQL's stock
  `DEFAULT_PGSOCKET_DIR "/tmp"`; it is an upstream constant, not a build path,
  and is the only match for a naive `grep -r /tmp`.
